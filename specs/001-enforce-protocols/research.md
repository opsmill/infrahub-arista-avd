# Research: Enforce Protocol-Typed Access

**Branch**: `001-enforce-protocols` | **Date**: 2026-02-10

## Decision 1: Protocol class availability for string-kind replacements

**Decision**: IpamIPPrefix and IpamIPAddress protocol classes already exist in `protocols.py`. Only the 7 Routing namespace types (`RoutingBGPPeerGroup`, `RoutingBGPNeighbor`, `RoutingPrefixList`, `RoutingPrefixListEntry`, `RoutingRouteMap`, `RoutingRouteMapEntry`, `RoutingStaticRoute`) need to be generated.

**Rationale**: Verified by reading `src/solution_ai_dc/protocols.py` — IPAM protocols exist at lines 200-231; Routing types are defined in `schemas/routing/routing.yml` but have no corresponding protocol classes. `NetworkPod` also already exists (used by hostvar generator fix).

**Alternatives considered**: None — `infrahubctl protocols` is the canonical generation method per constitution.

## Decision 2: avd_fabric_doc.py transform — scope of fix

**Decision**: The transform needs three changes: (1) the GraphQL query is missing `avd_artifact` fields the code tries to access, (2) the existing Pydantic query model (`avd_fabric_devices_query.py`) is incomplete, and (3) the transform code uses raw dict access.

**Rationale**: Lines 46-50 of `avd_fabric_doc.py` access `device.get("avd_inputs", {})` and `device.get("avd_structured_config", {})`, but the GraphQL query (`avd_fabric_devices.gql`) does not request these fields. The correct data path is through the `avd_artifact` relationship to object store identifiers, matching the pattern in `avd_eos_config.py` and `avd_device_doc.py`.

**Alternatives considered**:
- Only converting dict access to Pydantic (keeps broken data path) — rejected because the underlying query is wrong.
- Rewriting query to include inline structured config — rejected because structured config is stored in object store, not as a node attribute.

## Decision 3: avd.py `Any` types — dead code discovery

**Decision**: The two functions with `Any` types (`extract_uplink_info` and `build_fabric_hostvars`) are dead code — not called anywhere in the codebase. The recommended approach is to either remove them or add proper protocol types.

**Rationale**: Grep for callers found zero references. The AVD generator workflow was refactored: `generate_avd_device_hostvar.py` has its own `extract_uplinks_from_dict()` function that works with Pydantic query models. `build_fabric_hostvars()` is not used because the current architecture builds hostvars per-device, not per-fabric.

**Alternatives considered**:
- Remove dead code entirely — simplest, reduces maintenance burden.
- Replace `Any` with protocol types and keep for future use — adds type safety but maintains unused code.

## Decision 4: Pydantic query model generation method

**Decision**: Pydantic query models in this project are hand-written, not auto-generated by ariadne-codegen. There is no codegen configuration for transform/generator query models.

**Rationale**: No ariadne-codegen configuration found in `pyproject.toml` or `.graphqlrc.yml` for query model generation. All `*_query.py` files follow a consistent hand-written pattern with `Field(alias=...)` mapping and `.model_rebuild()` calls. The `ariadne-codegen` dependency exists only as an override for infrahub-sdk compatibility.

**Alternatives considered**: Setting up ariadne-codegen auto-generation — rejected as out of scope for this feature and would change the established project pattern.
